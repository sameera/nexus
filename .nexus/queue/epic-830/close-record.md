# Close Record: Close becomes a deterministic subcommand

## Key Decisions

- **D1 — The subcommand is named `nexus close` (#872).** The command is `nexus close`. It takes the arguments `/nxs.close` takes today: `--pr`, an optional entry path and `--handoff`. Recovery is a mode of the same command, addressed at the epic. **Why:** The stage is called close everywhere: in the pipeline sentence, the product context and `/nxs.close`. So the habit maps one-to-one, and the command sits with the existing close-family verbs `close-role` and `close-migration`. **Refuted alternative:** `nexus close-epic`, which follows the verb-object form of `create-epic` and `create-story`. It loses because the one-command close-and-distill script already uses that name, and its concept page lists "close-epic command" as an alias, so "run close-epic" would be ambiguous between a command that only closes and a script that also distills.
- **D2 — No model fallback: anything the verdicts lack is a stop (#872).** Close builds its content only from the verdicts, the record body and the issue graph. A merged pull request whose verdict has no judgments block, because it was published before #829 or by an older release, stops close, and the stop names a full `/nxs.analyze --pr` run on that pull request. Close never mines the diff, decision stubs, notes or story-issue comments, and has no model path for old verdicts. **Why:** The initiative requires zero model passes. A fallback would keep the whole mining stage alive as a second source of the close record. Writing a record without that pull request's judgments would silently drop rationale distill can never get back. **Refuted alternative:** Fall back to today's model mining for a pull request whose verdict has no judgments. In-flight epics would close without re-analysis. It loses because it keeps two close-record writers that can disagree, and the one-command script would need a model stage again for those epics.
- **D3 — Every gate runs before any write, and every gate ends in a stop, never a question (#872).** Close runs every gate before it cuts a worktree, writes a file or writes to GitHub: the role, the merged pull request, an unambiguous epic, every sub-issue closed, the #849 evidence gate with only posted waivers, zero open critical and high counts on each merged pull request's verdict, and a judgments block on each of those verdicts. A blocking verdict stops close, and the stop names answering on the pull request and then the analyze run that records the answers (#871 D4 and G17). Close never reads raw answers itself. Every stop prints one block with the reason, the item and the remedy, and exits non-zero. A waiver stop prints the exact form of the comment to post. **Why:** With no checkpoint, the only safe moment to refuse is before anything happens. A stop then leaves nothing to clean up. Reading answers only through the verdict keeps one source of truth, as #871 settled. **Refuted alternative:** Let close run the answer reader directly and apply a trusted "waived" answer that is on the pull request but not yet in the verdict. It saves an analyze run. It loses because the verdict and the close record would then disagree about which items are open, and it would re-decide #871 G17.
- **D4 — Code owns the close record's shape; the seeded template is no longer read (#872).** Close renders the close record and the close comment in a fixed shape that lives in code: today's frontmatter keys, Key Decisions, Deviation Rationale, Deferred Scope, Waived Stories and #849's additive range, landed-file and waiver stamps, with the Process Lesson section removed. Close no longer reads the seeded close-record template. Seeding stops placing that template, and a copy already in a repository is left alone and ignored. **Why:** A tuned template can carry placeholders only a model can fill "as the template's guidance says", and one-line list placeholders that must expand to many entries. Deterministic code cannot honour arbitrary placeholders. A fixed shape in code also makes distill's inputs testable (G15). **Refuted alternative:** Keep reading the template, fill the known placeholders, and stop on any unknown one. A project could keep its customisations. It loses because an unknown placeholder would stop every unattended close in that project, and close is the template's only reader, so keeping it costs a parser for one consumer.
- **D5 — How Key Decisions are assembled across several pull requests (#872).** Key Decisions has two parts. First, every decision of the approved record body, taken from the record issue's current body, which must hash to the `record_hash` close stamps, in record order, each with its ID, decision, reason and refuted alternative. An old-format record gives its decisions by title, and a record in neither format gives the text the verdict carries. The record-decision IDs in the verdicts are only checked against the body. Second, every stub a verdict confirms, listed once in the merge order of the first pull request that confirmed it, deduplicated by the stub's own identity. An epic with no record has the stubs only. **Why:** #871 D6 settled that the key decisions are every record decision plus the confirmed stubs, and #871 D5 settled that record decisions are carried by ID and resolved from the body the digest pins. Taking the text from the body close stamps means the close record and distill's own record fetch describe the same bytes, also when a revised-record waiver means the verdicts were judged against an older revision. **Refuted alternative:** Take the record-decision text from the revision each verdict stamped, found through the revision comments on the record issue. It would be exact per pull request. It loses because a waived revision would then put text from two revisions in one close record, and distill verifies the record against the current hash only.
- **D6 — Deviation Rationale is one entry per accepted departure per pull request (#872).** Each accepted departure becomes one bullet, in pull-request merge order and then ID order. Each bullet names the record issue and the element it departs from (or the epic's description when the epic has no record), the pull request and the departure's ID, what the code does instead, the accepted reason, and who accepted it with a link, or "the record revision". Departures from different pull requests are never merged. Items no longer found, and departures cleared by a code change, are not written. A waived critical or high finding is not a departure; it is listed with who waived it, in the waivers statement #849 added. **Why:** #865 requires each departure to name who accepted it. Two pull requests departing from the same decision are two facts, each with its own answer, and merging them would mean choosing one. **Refuted alternative:** Merge departures that cite the same record element into one bullet that lists both answers. It is shorter for a multi-pull-request epic. It loses because the merge rule would have to decide when two answers say the same thing, and that is a judgment.
- **D7 — The `analyze:` value keeps today's grammar (#872).** `analyze:` is `ran <date> @ <head>`, from the completing pull request's verdict. A revised-record waiver adds today's clause, `stale — record #<r> revised since analysis (<old> → <new>); waived <date>`, plus the waiver's author. The "closed without analysis" and "overridden" clauses are retired, as #849 D6 and #871 D4 already decided. Waivers for a landed-file mismatch and for findings go in #849's additive stamps, not in this value. The machine block keeps every key. **Why:** Distill's recovery from the epic issue compares this value with the verdict of the epic's linked pull request. Keeping the grammar, from the most recent pull request, keeps that comparison unchanged. Per-pull-request details already live in #849's stamps. **Refuted alternative:** One clause per merged pull request, joined in one string. It is more informative. It loses because it changes the format of a value distill's recovery reads, which counts as a change to distill's inputs.
- **D8 — Copied text is neutralised, not refused (#872).** Answer reasons, stub text and proposal text are copied into the close record, the close comment, the amendment and the stub bodies. Before they are copied, any close-record marker and any fence sequence in them is made inert. Frontmatter values are written only from values close computes, never from copied text. **Why:** Distill's range reader takes the first close-record marker in the file before it looks at the frontmatter, so a reason containing the marker and a fenced range would forge the range distill diffs. Stubs can be written by agents. Refusing would stop close on any reason that quotes a code block. **Refuted alternative:** Stop close when copied text contains a marker or a fence. It is simpler and obviously safe. It loses because reasons that quote code are common, and each one would cost an unattended run a stop.
- **D9 — Approved deferred scope is filed with find before write, keyed on the stub body (#872).** Close files each approved proposal from the newest verdict of every merged claiming pull request as one stub, through the existing batch filing path, with the epic classification and the unplanned label and no parent. The stub's body holds the proposal's goal (also its title), the feature path, its provenance (the epic, the pull request, the proposal ID and the approver) and the stub key. It holds no estimate and no ordering edges; planning sizes it. Before filing, close lists the issues that mention the epic, through the platform's back-references and never search, and reuses any stub whose key matches. The numbers fill Deferred Scope before the close record is committed. **Why:** With no checkpoint, a re-run has to be safe without the batch filer's local ledger, which lives in a worktree that may be gone. The back-reference already exists for every stub, because the body names the epic, and it survives a promotion that clears the unplanned label. Search is eventually consistent and could miss a stub filed a moment earlier. **Refuted alternative:** Rely on the batch filer's resume ledger, kept in the distill worktree. It needs no new lookup. It loses because a re-run on another day or machine, or after the worktree was removed, files every stub again, and duplicate issues are the one failure no later stage can undo.
- **D10 — The storyless waiver is a trusted comment on the story's own issue (#872).** A story with no claiming pull request passes the gate when it already carries the marker, or when it carries a trusted comment in the fixed waiver form on its own issue, with trust decided against the issues repository by the existing filter. For a waived story, close writes the marker before the close comment, and Waived Stories names the story and the date of the waiver comment. **Why:** Today this waiver is answered at the checkpoint, which no longer exists. The story has no pull request to carry a comment, and its own issue is where the marker is written. **Refuted alternative:** Accept the waiver as a comment on any merged pull request of the epic that names the story. It reuses #849's pull-request reader unchanged. It loses because which pull request to use is arbitrary, and pull-request trust is checked against the code repository while the story and its marker live in the issues repository.
- **D11 — Write order and resuming a re-run without a checkpoint (#872).** The order is stubs, markers, commit and push of the distill branch, amendment, close comment, closing the epic issue, hand-off note. Every GitHub write uses find before write. A re-run reuses the distill branch an earlier run created for this epic, local or pushed, and never cuts a second one. A push failure stops close before the amendment and the close comment, with the epic issue open; today close continues past a failed push. A failed close comment leaves the epic issue open, and the stop names re-running `nexus close`, which rebuilds the same body from the verdicts. Once a trusted close comment for the epic exists, a re-run regenerates nothing and only closes the issue, writes the hand-off note and reports. **Why:** Stubs come first because the record must name their numbers before it is committed. The push comes before the comment, so a closed epic always has a pushed entry for distill. The comment is the durable copy, so it decides "done". Without a person to read an "ACTION REQUIRED" line, the state after any failure must be one a plain re-run finishes. **Refuted alternative:** Keep today's behaviour on push failure: post the comment and close the issue anyway, so the rationale is durable at once. It loses because the epic then reads as closed while no branch exists for distill, the script refuses to continue, and a re-run would have to rebuild a branch for an epic it believes is finished.
- **D12 — The record amendment is built from superseding marks (#872).** When any verdict marks an accepted departure as superseding, close posts exactly one comment on the record issue, with today's heading and shape. For each superseded decision it gives the decision's text from the record body, what the code does instead from the departure, and why from the accepted answer. The comment carries a hidden key naming the epic, which find before write uses. With no marks, close posts nothing. The amendment stays advisory. **Why:** This is today's amendment output, with the model's judgment replaced by #871's mark. The key makes a re-run safe. **Refuted alternative:** none
- **D13 — Re-stamp recovery is deterministic, and a waiver or a fresh analysis says whether the change matters (#872).** Code cannot tell a wording-only revision from a design change, because a reworded guarantee keeps its ID and changes its text exactly as a redesigned one does. So recovery reads that judgment from where a person or analyze has already given it. If the record is open, recovery stops and names approving it. For each merged pull request: if the newest verdict was judged against the current revision, recovery rebuilds Key Decisions and Deviation Rationale from those verdicts; if instead a trusted waiver accepting the current revision is on the pull request (#849 D11), recovery keeps the Deviation Rationale and takes the record decisions from the new body. A pull request with neither stops recovery, which names re-running `/nxs.analyze --pr` on it or posting the waiver. The waiver is one comment per merged pull request, through #849's reader as it is. Recovery then re-stamps `record_hash` and the `analyze:` value, commits the entry, and posts a fresh close comment so distill's recovery from the epic issue finds the new hash. It files no stubs and posts no amendment. **Why:** The stories need a deterministic split. A waiver is the existing, recorded, trusted form of "this revision does not change what the code must do", and analyze is the existing judge of a design change. Today's recovery leaves the close comment stamped with the old hash, so a lost entry could never drain. **Refuted alternative:** Compare the decision and guarantee lists of the old and new bodies, and treat "same IDs" as wording only. It needs no lead action. It loses because a guarantee rewritten to mean something else keeps its ID, so the check would re-stamp a design change silently.
- **D14 — The process lesson is removed at every writer, and discover keeps its note (#872).** Close writes no lesson file. The close record has no Process Lesson section, and the close comment has no lesson pointer. Setup no longer creates the lessons folder or its README, and its summary no longer lists them. Discover's closing step creates the folder when it is absent and drops its sentence that the folder "already holds" notes written by a pipeline stage. The lesson mention in distill's mode-detection text may be fixed as a text-only edit, as the initiative permits. **Why:** Nothing reads the lesson (initiative D-D.2). Discover's note is the only record of a discovery closed with no build, so its folder must still appear on demand. **Refuted alternative:** none
- **D15 — `/nxs.close` becomes a relay with no end date (#872).** Without `--pr`, `/nxs.close` refuses with today's text, before any other step. With `--pr`, it runs `nexus close` with the same arguments, relays the output unchanged, and ends with one line telling the lead to call `nexus close` directly next time. It does not interpret, retry or fix a stop. Its description drops the checkpoint and the interactive tool. It keeps one section under today's recovery title, which names the recovery mode, because distill's hash-mismatch message points at that title and distill must not change. The relay has no end date; removing it is left to a later epic that also edits distill's remedy text. The pipeline sentence in the project guide, close's description and the PR-driven delivery docs are updated in the same story. **Why:** This keeps the habit and the distill pointer working with no change to distill. A relay that acted on a stop would bring back model judgment. **Refuted alternative:** Remove `/nxs.close` and let the harness report an unknown command. It is less to maintain. It loses because #869 commits to keeping the habit, and distill's remedy text would point at nothing.
- **D16 — The script calls `nexus close` directly, reads a stop from the exit status, and keeps the hand-off check (#872).** The close stage of the one-command script becomes a direct call to `nexus close` with the hand-off path. There is no harness session, so the Codex entry point behaves the same by construction. On a non-zero exit, the script repeats close's stop block and starts no distill. On success, it still checks the hand-off note against the platform and git before starting distill. The interactive-stage helper is removed. **Why:** A deterministic command's exit status is reliable. The rule against trusting exit status existed because a model stage exits 0 when it stops. Keeping the note check costs nothing and keeps the existing guarantee about when distill starts. **Refuted alternative:** Call `/nxs.close` headless through the harness, as distill is called. The script would stay uniform. It loses because it puts a model pass back in front of a deterministic command and loses the exit status.
- **D17 — Release coupling and versioning (#872).** `nexus close` can land story by story, but nothing calls it until the switch. The switch is #869 and #870, replacing `/nxs.close` and the script's close stage. It ships in one release with #866 and #867, and no earlier than #829's release (#871 R7). #869 therefore also waits on #867, because the old recovery instructions live in the command document #869 thins. Each story that changes a component bumps the version, with its changelog entry, in the same commit. The switch release's entry states the change as breaking: close no longer asks anything; waivers and answers must be posted on the pull request and recorded by analyze before close runs; the storyless waiver is a comment on the story issue; in-flight epics with verdicts from before #829 need a full analyze run; no lesson is written; a tuned close-record template is ignored; the direct command is `nexus close`. **Why:** This is the initiative's same-release rule: close's mining and checkpoint go only together with the close that reads the verdicts. If `/nxs.close` were thinned before recovery and filing exist, closed entries could be stranded. **Refuted alternative:** none

## Deviation Rationale

- **Departs from record #872 D6 — sameera/nexus#879 DV6.** Close's main path now reads verdicts in merge order (close-ranges.ts:381, close-command.ts:428), but nexus close --recover still orders them through stampedPrs, ranged pull requests first and any with no range after (close-record.ts:579-603, close-recovery.ts:145). Recovery's rebuilt Deviation Rationale and its completing pull request for analyze: (D7) can still be out of merge order; the close comment stamps no merge date to rebuild it from. **Why:** recovery cannot rebuild merge order because the close comment stamps no merge dates; only pull requests that changed no files are affected **Accepted by:** @sameera (https://github.com/sameera/nexus/pull/879#issuecomment-5985965956)
- **Departs from record #872 D11 — sameera/nexus#879 DV7.** D11 says that once a trusted close comment exists, a re-run regenerates nothing and only closes the issue, writes the hand-off note and reports. The re-run now also reads the record and the stamped verdicts and posts a missing amendment (close-command.ts:640, 671-711), which G26 and G28 call for. **Why:** G26 and G28 require a re-run to finish a failed amendment; D11's "regenerates nothing" predates that **Accepted by:** @sameera (https://github.com/sameera/nexus/pull/879#issuecomment-5985965956)
