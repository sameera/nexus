# Close Record: nexus implement --retroactive builds an epic that has no decision record

## Key Decisions

- **D1 — The flag changes the run only when the epic has no record sub-issue (#1051).** The issue graph decides at preflight whether the epic has a record sub-issue. The flag removes the "needs design and has no record" refusal only when there is none. With an open record the run refuses as today, and with an approved record it runs as an ordinary run and says the flag was not used. The retroactive notice is written when the pull request is created, outside the status section. **Why:** #1042 needs three behaviours, and one test against the issue graph, before any agent runs, gives all three. The path without the flag stays unchanged, because the flag removes one refusal and only when there is no record. A notice outside the status section survives every later stop, because a stop rewrites only the status section. **Refuted alternative:** let the flag override an open record too, and build without waiting for approval. A lead stuck on an unapproved record would find that convenient. It lost because it turns "approve the record" into "ignore the record", and the epic refuses it explicitly.
- **D2 — Agent-written text reaches the pull request only quoted inside its body (#1051).** The command quotes agent-written text into the pull request body. Neither the agent nor the command posts it as a comment. **Why:** Nexus stages trust answer and waiver lines in pull request comments from an account that can speak for the repository, and the command posts under the lead's account. A plan posted as a comment could therefore carry an agent-written "accepted" or "waived" line that reads as trusted. The body is not read for answers, but GitHub reads it for closing references, and close relies on those for story claims, so the text must be quoted until it is inert. The run's existing guard catches only answer lines that appear during an agent stage, and a comment posted before the first analyze round would escape it. **Refuted alternative:** commit the plan file on the run branch, which makes it reviewable in the diff. It lost because it breaks the one-commit-per-story check and puts planning files into the repository, which the product rules out.
- **D3 — Planning is its own agent session before the build, and it is never enforced (#1051).** In a retroactive run, after preflight and branch creation, the command runs a planning session on the planning model (D10, D11). The session reads the epic and the checkout and ends with its plan as its final message, which the command writes to the plan file in the run scratch folder. The command then checks the checkout, and if the planning session left any file change, commit or branch move, the run stops before the implementation stage. The implementation stage receives the plan as guidance, and the epic's acceptance criteria bind. It is also asked to keep the choices log in the run scratch folder. A planning session that fails, cannot start or ends with no plan does not stop the run: the implementation stage runs without a plan, and the pull request says that no plan was produced and why. **Why:** One harness session runs on one model, so a plan on Opus needs its own session unless the whole build runs on Opus. The command captures the plan from the final message, so the plan exists even when the agent writes no file. The checkout check keeps planning read-only in the same way on both harnesses. #1043 and the epic's Out of Scope rule out checking that a plan exists. The choices log is the only place where the reasons behind the build survive; without it, the as-built record would rebuild its reasons from code. A folder git ignores keeps the checkout clean for the story-commit check. **Refuted alternative:** keep the plan request inside the implementation session. It costs one session fewer, and the agent keeps its own plan in its reasoning. It lost because that session's model also builds every story, so either the whole build pays for Opus, or planning never runs on Opus.
- **D4 — The as-built record is filed and approved before the first review round (#1051).** The as-built record is filed and approved after the story-commit check and before the first review round, not after the fix loop. **Why:** Analyze today stops on an epic that needs design and has no record. Filing first means analyze, close and that rule stay unchanged. The fix loop already refuses architectural changes and escalates them, so the design is settled when the implementation stage ends, and the record stays accurate through the fixes. The story-commit check is the command's one authority for "every story built", which is exactly #1044's condition for filing no record on a partial build. A loop that stops later still leaves the epic with its approved record, and the lead can continue by hand with `/nxs.analyze --pr`. **Refuted alternative:** write the record after the fix loop finishes, so it reflects every fix. That is closer to the epic's assumption that review runs with no record. It lost because analyze would need to accept an epic that needs design and has no record, a new bypass in another stage that no story delivers. A loop stopped by the round cap would also leave such an epic with built code and no record, and the lead would have to approve decisions they did not take.
- **D5 — A separate agent session writes the as-built design document and the decision-record stage files it (#1051).** A separate as-built stage writes the as-built design document and hands it to the decision-record stage through `--from`. The command does not file the record itself, and the implementation agent does not write it. **Why:** This follows the lead's suggested route and reuses the import path, which already treats a document as the design's authority and checks that every story is covered. A fresh session after the story-commit check is the only placement that meets #1044's condition about a partial build, because the implementation agent's session ends before that check and its turn budget is spent. Filing stays in one implementation, the stage's own filing phase, with the shared checker, the derived body, the labels and the pinning. **Refuted alternative:** have the command file and close the record itself from an agent-written body. That is fully deterministic and needs no stage change. It lost because it would be a second implementation of filing, covering marker classification, labels, the derived body, the digest and source pinning, and that copy would drift from the stage. Preventing that kind of drift is why the razor-enforcement and publishing-config-resolution pages exist.
- **D6 — The decision-record stage gains an as-built mode chosen only by a switch that names the run's pull request (#1051).** In as-built mode every interactive stop of the decision-record stage is replaced by a defined run decision, and the record opens with the as-built statement. Only an explicit switch that names the retroactive run's pull request selects the mode. **Why:** #1044 requires the hand-run stage to keep its stops, so the unattended behaviour has to be a separate mode the run opts into, not one inferred from running headless. Requiring the pull request reference, and checking that the pull request is the epic's open retroactive run, ties every as-built record to a run a reader can find. That makes "the run decided" a checkable claim and makes the switch hard to type by accident. The close event is recorded under the lead's account, because the run has no account of its own, so the statement in the body is the only honest attribution available, and it stays plain prose. **Refuted alternative:** detect a headless run and answer the gates automatically. It needs no new switch. It lost because it silently changes the stage for anyone who runs it headless for another reason, which breaks #1044's hand-run criterion, and the record would carry no link to a run.
- **D7 — A draft with anything only the owner can accept is not filed (#1051).** An as-built draft that holds anything that would be placed under "Resolve before approval", such as a BLOCKER risk or an ADDRESS risk that another epic delivers and nobody has accepted, is not filed. The run stops before review. The lead chose this at this record's clarification gate. **Why:** Those items exist because only a person can accept them, and a run approving past them would be a gate that cannot refuse. "Before implementation" is empty by construction, because the build is done. Every other group of the approval brief keeps the approval-brief page's placement rules unchanged. **Refuted alternative:** file and approve anyway, listing the items for the lead to read on the pull request. It never stops the run, which matches the epic's "without waiting for the lead". It lost because the epic promises that the run decides what the design is, not that it accepts risks on the owner's behalf.
- **D8 — The run confirms the record on GitHub before review and shows it on the pull request (#1051).** After the as-built stage, the command goes on to review only when it has confirmed the record from the issue graph. It then names the record on the pull request and quotes the stage's checkpoint list and observations there. **Why:** A stage that filed but did not close, or filed a record without the statement, would otherwise reach analyze as unapproved, or as a record that reads as approved by the lead. Quoting what the model added, and the shared checker's observations, onto the pull request lets the lead see them while reviewing the build, which keeps observations in front of a person when no checkpoint reviewer exists. **Refuted alternative:** none
- **D9 — The distiller keeps the as-built attribution in the decision-log entries it writes (#1051).** When the distiller carries an as-built record's reasons into the concept store, each decision-log entry it writes states that the retroactive run, not the lead, decided it. The distiller recognises an as-built record by the as-built statement at the opening of its body. The lead added this to #1044 at this record's clarification gate. **Why:** Decision-log entries cite only the epic number. Without the attribution, a reason the run decided becomes durable reasoning in the concept store that reads like the lead's decision, which the epic rules out. **Refuted alternative:** mark an as-built record with a label on its sub-issue and have the distiller read the label. A label is easier for a machine to read. It lost because a label sits outside the hashed body, so it can be added or removed without changing the record's digest, while the statement in the body is covered by the digest that close stamps.
- **D10 — Planning and implementing models are set per harness in the settings file (#1051).** The settings file gains a top-level `claude` section and a `codex` section, named exactly like the `--harness` values. Each section holds a planning model and an implementing model. Each of the four keys is one entry in the key catalogue that records its section, so each key gets the precedence chain, the hub's own settings layer, `nexus config resolve` and the settings writer with no second implementation. The keys are not repository-specific, so a repository in a workspace inherits them from the hub's own settings. They are not added to the workspace manifest's defaults; the lead chose this at this record's clarification gate. The order, highest first, is the run's planning-model or implementing-model option, the repository's harness section, the hub's own harness section, and the built-in. Only Claude Code's planning model has a built-in: Opus, named by the harness's alias for the newest Opus. The planning-model option without `--retroactive` is a usage error. **Why:** The lead asked for one section per harness, with a planning and an implementing model. A model name only makes sense for one harness, so keying it by harness section stops a hub's Claude model from reaching a Codex run. Putting the keys in the one catalogue keeps the publishing-config-resolution page's invariant 1, because nothing parses settings itself. The Opus built-in keeps the lead's rule for a repository that sets nothing. The options follow the precedence chain's top layer, as the test-command option already does. **Refuted alternative:** flat keys with a harness prefix inside the existing GitHub publishing block, such as a Claude planning-model key. It needs no reader or resolver change, and it is the arrangement #178 chose for the worktree path. It lost because the lead asked for sections, a model choice is not a GitHub publishing setting, and prefixed keys hide the grouping by harness the lead wants to see.
- **D11 — With no planning model set, planning runs on the implementing model and the run says so (#1051).** When no layer gives a planning model, as for Codex by default, the planning session runs on the implementing model, or on the harness default when no implementing model is set either. The run prints one line, and the pull request says which model planned and why. **Why:** The plan is never enforced, so refusing the run would be out of proportion. The lead can set a Codex planning model in the settings, so the fallback is a state the lead can end at any time. **Refuted alternative:** refuse a Codex retroactive run before it starts until a planning model is set. It is explicit, and it can be decided before any agent runs. It lost because it breaks the epic's one-command success metric by default for a step the epic never enforces.
- **D12 — The as-built stage runs on the model the planning session ran on (#1051).** The as-built stage uses the model the planning session ran on. When the planning session could not start, for example because the account cannot use the planning model, the as-built stage uses the implementing model, or the harness default when none is set, and the pull request says so. **Why:** The as-built stage writes the run's most durable output: the approved record and the reasons the distiller carries into the concept store (D9). The lead's reason for planning on Opus applies to it at least as strongly. Without the fallback, an account with no Opus access would get no plan, which G7 allows, and then a certain stop at the as-built stage after the whole build. **Refuted alternative:** run the as-built stage on the run's ordinary model. It is cheaper and keeps to the lead's literal words, "for planning". It lost because the record outlives the plan, and it is the one artifact the run approves for itself.
- **D13 — A configured implementing model runs the build and the fix rounds of every run (#1051).** A resolved implementing model goes to the stages that write code, the implementation stage and each fix round, in runs with or without the flag. Analyze is a review stage and gets no model from the command, though it still gets any model in the pass-through arguments, as today. A model in the pass-through arguments wins over the settings for the stages it reaches. The implementing-model option together with a model in the pass-through arguments is a usage error. When nothing is set, the command passes no model, as today. **Why:** The lead asked for an implementing model per harness, which is a property of every build, not only of retroactive runs. Applying it only when it is configured keeps the epic's promise for every unconfigured repository. **Refuted alternative:** apply the implementing model only in retroactive runs. It leaves the path without the flag untouched with no condition. It lost because a team that sets an implementing model would see it silently ignored in ordinary runs, a setting that works only half the time.
- **D14 — Model values are checked before anything runs (#1051).** Before any agent runs, every resolved model value must be one plain token. The run refuses a value that starts with a dash, contains whitespace or is declared empty, and the refusal names the value and the layer it came from. A key the catalogue does not declare in the selected harness section gets one warning line. A section for a harness the command does not support is ignored. A model the account cannot use is found where it fails: planning continues (G7), an implementation or fix stage stops the run as today with the model and its layer named, and the as-built stage falls back (D12). **Why:** The value becomes an argument to the coding agent, and it can come from a hub's settings. A value read as an option could widen the agent's permissions, which the unattended-epic-implementation page's invariant 2 forbids. A misspelt key only costs the default model, so refusing over it would be out of proportion. **Refuted alternative:** refuse any unknown key in a harness section. It catches every typo. It lost because a harmless typo would block a run the lead started unattended, and the warning line already names it.
