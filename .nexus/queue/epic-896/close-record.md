# Close Record: Planning and Conformance Read the Concept Store

## Key Decisions

- **D1 — The reading list is built by a deterministic phrase match over page frontmatter, plus one step of neighbours (#902).** The list builder proposes direct matches and their neighbours. It skips pages that are not active and never follows a neighbour's neighbours. No model adds or removes pages; the reviewer does that at the digest. Promoting a backlog stub runs the list builder like any new draft, including a stub filed before this change. The Out of Scope line excludes only backfilling epics that are already planned. **Why:** These are the store's own retrieval paths: a term or synonym matches the title and alias lines, and the neighbour list is not transitive. A deterministic builder gives the same list for the same intent, and it can be tested. The store already holds that a rule a gate depends on must not have a non-deterministic executor. The success metric asks for an intent that names a concept, and a phrase match is exactly that test. Adding the drafted title and Description to the match text covers promotion and discovery modes, whose raw input is not prose intent. **Refuted alternative:** Let the epic-stage model read every page's frontmatter and judge relevance. It would catch paraphrase that a phrase match misses. It lost because the list would change between runs and could not be tested, and the reviewer already corrects misses at the digest at no cost.
- **D2 — The cap is seven pages in total, direct matches first (#902).** A reading list holds at most seven pages, direct matches and neighbours together. Direct matches fill the list first, in order of first appearance. Neighbours fill the rest, those named by more matches first. Everything beyond seven is an overflow page, offered unticked at the digest. **Why:** The store already fixes this number. The concept-page-capacity page budgets about six thousand words "across the seven pages one task may load", and the grep-native-retrieval page caps neighbour loading at "a handful of pages per task". Seven makes that handful concrete without inventing a new budget. Direct matches come first because the intent named them, while neighbours are only likely to matter. Hub pages show why neighbours must be bounded: the distiller page names 29 neighbours and the conformance-gate page names 16, so one match on a hub would otherwise fill any list. **Refuted alternative:** Cap only neighbours, for example at three, and take every direct match. Direct matches are the most relevant pages, so dropping one costs more than dropping a neighbour. It lost because a broad intent can name ten or more concepts, and an unbounded list breaks the per-task load budget the store records.
- **D3 — The reviewer edits the reading list inside the digest's existing numbered selection (#902).** The reading list is shown as its own group in the digest's numbered checklist. Proposed pages are ticked, each with the reason it was proposed, and overflow pages are unticked. One typed selection flips pages and stories together. The cap is hard for the reviewer's set: a selection that leaves more than seven pages ticked is refused and returns to the choice. Adding a page that was not offered is done through revise, by editing the draft's frontmatter. A resumed draft keeps whatever list it carries. The approved list is written into the draft before the filing body is derived. **Why:** The digest is the approval surface, and the store already holds that one typed selection carries the whole decision. A second interaction would split one approval into two. The checklist is generated by the toolkit, so the reading-list lines and their numbers cannot drift from the draft. The cap exists to bound the architect's input, and a reviewer-only bypass would make it advisory. **Refuted alternative:** Show the list as plain text in the digest and take changes as free text in the approve-with-changes answer. Any page could then be added in one step. It lost because free-text page names are unchecked input at the one gate that files irreversibly, and a mistyped name would reach the issue.
- **D4 — The list travels in the existing hidden epic-metadata block, and it names pages to read, never pages to write (#902).** No new carrier is added. The reading list rides the epic issue's existing metadata block and returns through the resolver verbatim. An absent list reads as an empty list in every stage. The list holds page names only; no page text is copied onto any issue. No stage writes the store from the list, and the distiller still infers its own mapping. **Why:** The block already carries the raw planning frontmatter, and the resolver already returns it unchanged; an existing test pins the list surviving the round trip. A second carrier would be a second copy that can go stale. Keeping the distiller off the list preserves its recorded reason for inferring the mapping itself: a list made before the code exists guesses concept boundaries. **Refuted alternative:** A visible "Reading list" section in the epic issue body. The team would see the list on the issue. It lost because the body is edited by people and transcribed into story bodies, so the list would exist in two places with no rule for which one wins.
- **D5 — The architect reads each listed page whole; a missing page is named and skipped (#902).** The record stage passes the full text of each listed active page to the architect, decision log included. This replaces today's instruction to search the docs for matching pages. A name with no active page is named in the run's output and in the pages-read sentence, and the run continues. **Why:** The story asks for summary, invariants and refuted alternatives. The first two have a fixed place on a page, but refuted alternatives live in decision-log prose with no fixed form. Their wording varies, and five pages carry no marker for them at all. Passing the whole page is the only way that never silently drops one. **Refuted alternative:** A toolkit step that extracts the summary, the active invariants and the refuted-alternative sentences into a compact brief. Architect input would be much smaller. It lost because the extraction depends on wording that varies, so it would miss alternatives without saying so, and those are exactly what this epic exists to stop being proposed again.
- **D6 — Concept-store changes is always present in a new-format record and opens with the pages-read sentence (#902).** In every new-format record at every size, the Concept-store changes section is present. It opens with the pages-read sentence, then lists the declared changes or says "No concept-store change." Both sentences are plain lines, not list items, so the section reader still lists only declared changes. The heading keeps its current name. **Why:** Stories #898 and #899 each require a positive statement when nothing was read or nothing changed, and the filed body carries no frontmatter to hold the list. Keeping the existing heading means the section reader, the distiller, the section-order check and every adopter's seeded template copy keep working without reseeding. The presence rule lives in the stage, not the template. **Refuted alternative:** A new "Concept pages read" section beside Concept-store changes. The heading would describe its content exactly. It lost because every reader and every seeded project template matches the current heading set, so a new heading forces each adopter to reseed and carry local tuning across.
- **D7 — A guarantee that keeps a listed invariant names the page and the invariant number in its sentence (#902).** Such a guarantee names the page and the invariant number inside its sentence, for example "as the concept-store page's invariant 7 requires". The closing decision citation stays last. A guarantee with no decision of its own goes under "Existing behaviour to preserve". **Why:** The section reader takes a guarantee's decisions only from a trailing parenthetical, so a page reference must sit before it. Page names are the store's only key; titles are not unique. **Refuted alternative:** none
- **D8 — A declared change quotes the page exactly, cites its decision, and is checked against the page before filing (#902).** Each declared change names the page, quotes the current statement, gives the new one, and cites the decision that causes it. The section reader is extended so the old and new statements are still split out when the decision is cited on the line. Lines in the current form keep parsing as before. At the pre-filing checkpoint, the quote check confirms each quoted statement appears on the named page with whitespace normalised, because pages hard-wrap their lines. A miss blocks filing and names the line. **Why:** The conformance gate decides whether an invariant is covered by matching the quote against the invariant's text (D10). A paraphrased quote would not match, and the gate would then flag an approved change. Checking the quote at drafting time catches the paraphrase while the draft can still be fixed. **Refuted alternative:** Let the gate judge coverage by meaning, with a model deciding whether a change is about an invariant, so no exact quote is needed. Drafting is easier. It lost because the gate's answer to "was this change approved" would then vary between runs on the same record.
- **D9 — Reversing recorded reasoning always counts as a trade-off, so the change reaches the approval brief (#902).** A decision cited by a declared change must state a trade-off that names the reasoning it reverses. Writing "none" is refused at the checkpoint. The existing rule that every decision with a trade-off appears in the brief exactly once then places it there. **Why:** The brief is built mechanically from decisions, and the checkpoint already enforces brief listing by ID. Making the reversal a trade-off reuses that enforcement instead of adding a brief group that every reader would have to learn. **Refuted alternative:** A new brief group, "Concept-store changes to approve". It is more explicit for the approver. It lost because it adds a third rule to the brief check, while the existing trade-off rule already guarantees a listing.
- **D10 — Analyze checks each listed invariant at the change's base, and skips the ones a declared change covers (#902).** The invariant lister reads each listed page as it stood at the base the change is diffed from; in a hub workspace it reads the page at the hub checkout. It lists every invariant that is not struck through and marks each one a declared change covers. The model judges only the uncovered ones. This runs in full mode and in degraded mode; with no record, nothing is covered. A missing page is named and the rest are checked. If the store itself cannot be read while the list is not empty, the run stops and publishes nothing, as a record fetch failure does. **Why:** Reading at the base means a pull request that edits a concept page cannot change what it is checked against. Making coverage deterministic means "was this approved" is a fact, not a judgment. Checking in degraded mode is what "never reaches close unapproved" requires when there is no record to declare a change in. Stopping on an unreadable store prevents a silent pass with zero invariants checked. **Refuted alternative:** Read the pages at the pull request's head. The newest store state would be used. It lost because the head is the code under review, and a branch could rewrite the invariant it breaks.
- **D11 — A concept departure rides the existing departure item and result kind, at severity high (#902).** A concept departure is an ordinary departure whose "departs from" text names the page and the invariant number. It does not mark itself as breaking a guarantee, so an unanswered one is high, not critical. It is numbered, answered, carried across runs and reported as no longer found by the existing machinery. Its judgment is recorded under the existing "guarantee" result kind, so answer-recording runs judge it again when its files change. The verdict's machine blocks gain no new field or kind. **Why:** The judgments block accepts only the criterion, guarantee and metric result kinds, and a reader from an earlier release rejects any other kind as malformed. A new kind would break close and the merge pre-check for a team running mixed releases, which must read normally. High still blocks close until answered, exactly as critical does. Severity high separates a recorded invariant the approver never approved again for this epic from one of the epic's own approved guarantees, and some recorded invariants are stale. **Refuted alternative:** A distinct result and item kind for concept invariants. Reports could filter and count concept departures separately. It lost on the cross-release parse failure, for a distinction the report line (D12) already gives a human reader.
- **D12 — The report states what was checked against the store (#902).** Analyze's report and published review gain one line. It gives the number of concept invariants checked and the pages they came from, or says that none were checked because the epic lists no concept pages, plus any listed page not found. It goes in the human-readable part, never the machine block. **Why:** Story #900 requires a stated result for an empty list. The store already holds that "nothing was checkable" must never look like "everything passed". **Refuted alternative:** none
