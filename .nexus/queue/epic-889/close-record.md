# Close Record: Stages Follow the Opus 5.5 Prompting Guidelines

## Key Decisions

- **D1 — One run-discipline skill holds the continue rule and the report layout (#905).** One shared skill is the single statement of both the continue rule and the report layout. It follows the razor skill's pattern: one normative home, with pointers elsewhere. Setup, discover, epic, decision-record, analyze, distill, fix, intake and the council load it at their start. Analyze and the council gain the tool that loads a skill. `/nxs.close` does not load it, because it runs one command and shows that output unchanged, so it has no pause to govern and no report of its own. The PM, architect and epic-gate agents do not load it either. They report to a stage, and that stage governs the stops and the report. **Why:** The epic asks for one shared place, and stages already load skills by name. Both rules apply to every stage, so one load covers both. Loading a report rule into `/nxs.close` would contradict its rule that it shows the command's output unchanged. **Refuted alternative:** Have setup write the continue rule into the adopter's own instructions file, as the guidance suggests. That needs no tool changes and also covers work outside Nexus. It lost because the epic's assumptions rule it out, and each adopter would carry a copy that drifts from the release.
- **D2 — What a stage stops for (#905).** The continue rule allows a stop only in four places: at one of the stage's gates; at its finish line; at a step the stage cannot finish without the lead, where it names what it needs; and before a destructive act that no gate or command argument has already approved. A destructive act is deleting data the run did not create, force-pushing, or rewriting history. The rule names three things a stage must not do: summarize without acting, offer to continue, and list choices that block nothing. The rule never touches permission prompts. In an unattended run, the stage's unattended rules decide what a gate does. **Why:** The guidance says to stop "before anything destructive: deleting data, force-pushing, or changing anything outside this repository." Read literally in Nexus, every GitHub write would become a new stop. That includes analyze publishing its review, which the lead asked for with a command argument and which has no gate today. Adding those stops would rewrite gates, and the epic's Out of Scope forbids that. So a write outside the repository stays governed by the gates that already come before it. The guidance's rule that permission prompts stay on is kept as written. **Refuted alternative:** Adopt the guidance's list of stops word for word. It is the closest match to the published advice. It lost because it adds a stop before analyze publishes and so changes gates the epic keeps.
- **D3 — The finish line also names the gates (#905).** Each stage's opening states what "done" means and names the gates where the stage stops for the lead. It stays in the stage's own opening, because it differs per stage. It does not go in the shared skill. Setup and the council have no Role heading, so their opening paragraph serves. `/nxs.close` gets one finish-line sentence. **Why:** The guidance has two parts: say what done looks like, and say when to stop and ask. The epic's criterion asks only for the first. The shared rule says "stop only at one of your gates", which means nothing unless each stage names its gates where that rule is read. **Refuted alternative:** none
- **D4 — One report layout, with machine-read lines kept in place (#905).** Every completion report a stage command writes uses Blocked on me, then Changed, then Found. When nothing waits on the lead, Blocked on me says so in one line, and that line names the next stage to run. Each stage moves its existing report content under the heading it belongs to. The epic stage's implementation sequence goes under Changed. Distill's counts and analyze's per-story results go under Found. Analyze uses one layout for both its terminal report and its published review: open critical and high items appear by ID under Blocked on me, with their detail under Found. Its fixed result line stays the last line, unchanged. Fix and intake turn their closing self-check into a line under Changed that says nothing else was written. The council's recommendation and the advisory agents' outputs are deliverables in their own formats, not completion reports, so they keep their formats. Analyze keeps listing medium and low findings. **Why:** This is the report form the guidance gives. Keeping the machine-read lines in place protects the script that runs analyze between implementation rounds, which reads its last line, and the verdict reader. Medium and low findings stay because their counts feed the receipt that close reads, and the epic does not ask to change that. **Refuted alternative:** Change only the terminal report and leave analyze's published review as it is. The review would keep its current look. It lost because two layouts over one summary can drift apart, and the engineer answering on the pull request also benefits from reading the blocking items first.
- **D5 — Advisory agents ask for a stated justification (#905).** In the PM agent, the line asking it to show its work and explain its reasoning becomes a line asking for each recommendation to be justified in at most three sentences. The quick format's Reasoning heading becomes Why, with one sentence per bullet. The line asking that others understand its reasoning without a meeting becomes a request for an analysis a reader can act on without a meeting. The PM agent's and the council's self-check blocks are removed. Each check either becomes an output requirement (state confidence, state what is unknown, name the assumption challenged, give concrete next steps) or is dropped where the output format already requires it. A repository-wide check confirms that no component asks for careful thinking, step-by-step thinking, shown work or reproduced reasoning. **Why:** The guidance says to ask for what you need instead, for example "Explain why you chose this approach in three sentences." The epic's justification of a stated length matches that. A search of the components found no "think carefully" or "step by step" lines. It found one "show your work" line in the PM agent and the two self-check blocks. **Refuted alternative:** none
- **D6 — Unconfirmed is analyze's state for criteria and guarantees, and it does not block (#905).** A criterion or guarantee that analyze cannot confirm from the code it read is marked unconfirmed. It names where the stage looked, by file or by surface, and what would confirm it. Unconfirmed replaces today's "unverifiable here" for criteria, such as a threshold that needs a benchmark. Success metrics keep "unverifiable", because there it means a measurement after release, which is a different question. Unconfirmed items have their own count on the severity line and are listed under Blocked on me as checks for the lead. They are left out of the open finding counts that the receipt, the merge pre-check, close and the result line read, so they never block. On a pull request, the machine record of each result carries the unconfirmed state, so a later run that records answers carries it forward like any other result. **Why:** The story says unconfirmed items are counted separately from findings and do not pass silently. Listing them where the lead reads first means they do not pass silently. Keeping them out of the finding counts keeps them separate. A run that records answers on an unchanged pull request carries forward only the machine record, so the state must live there or it would disappear from the next review. The lead confirmed at this run's clarification gate that an unconfirmed item never blocks. **Refuted alternative:** Report each unconfirmed item as a high finding, so the existing waiver path forces an explicit answer. That needs no change to the machine record. It lost because the story counts these items separately from findings, and it would block merges on gaps in the check rather than gaps in the build.
- **D7 — A run folder in the checkout, with a checklist that guards the final write (#905).** Each analyze or distill run gets one run folder in the checkout's ignored working area. It sits one level deeper than any queue-entry shape, as the planning run folder does, and its name comes from the run's subject. The stage's existing working files move into it. The checklist has a header naming the run, one line per item, and one line for the final external write. A line is ticked only after its item's result is saved, and a new item the run finds is appended. A new run always replaces the folder and never reads an earlier run's checklist. A run that reaches its finish line removes the folder. A run that stops early leaves the folder for the lead to inspect. **Why:** Neither stage defines where its working files live today, so a checklist path could be lost in the same summary it is meant to survive. A path the stage can derive from its own text and the run's subject can always be found again. Saving results beside the ticks lets the final table be built from files, which follows the guidance to read the file, not the scrollback. A ticked line for the final write prevents the worst duplicate, a second review or a second pull request. Replacing the folder at every start keeps distill free of carried-over state and stops a stale tick from skipping an item. **Refuted alternative:** Use the harness's built-in task list, which survives a summary in Claude Code with no file at all. It lost because Codex has nothing equivalent, and because the task list cannot hold each item's accepted evidence for the final table.
- **D8 — One general-purpose reader per item, with the evidence check in the stage (#905).** With more than one item, each item goes to its own general-purpose reader, and the readers run in parallel. Each reader gets the reader brief: read only, cite every claim in the evidence form, and mark what you cannot support as unconfirmed, with where you looked. The stage runs the evidence check. It checks a failing claim once more by reading the location itself, and otherwise marks it unconfirmed. Nothing is sent back to a reader. With one item there is no reader, and the stage uses the same evidence form. Analyze readers judge only their story's acceptance criteria. Distill readers return only behaviour changes and decisions, never deltas or prose. The final table goes under Found. For analyze, each row gives a story's counts of met, partial, unmet, contradicted and unconfirmed, with evidence locations but no quotes, so the published review stays inside the platform's size limit. For distill, each row gives an entry's outcome (drained, blocked or skipped), the concepts it changed, and the record decisions and diff locations behind them. This adds one field to the run summary that only the report shows, so the checkpoint and the pull request body stay as they are. Under Codex, the readers run one after another, and the run says so. The fan-out applies whenever there is more than one item, including the repeated analyze rounds during implementation. The lead confirmed that threshold at this run's clarification gate. **Why:** This follows the guidance's subagent pattern: one subagent per item, check its evidence before accepting it, and finish with one table. A mechanical quote check catches invented evidence, which is the main risk, without the stage redoing each reader's work. The stage still judges whether a real quote satisfies the criterion. Deriving the diff again in the reader keeps distill's rule that a diff is never stored. **Refuted alternative:** A dedicated read-only reader agent, like the epic gate. It would give the reader its own reviewed role file. It lost because the reader needs the shell to read diffs, so a tool restriction protects little, and the evidence form would be split across two files.
- **D9 — The epic may change three small parts of the executable's package (#905).** The executable's commands and behaviour stay out of scope, with three exceptions. First, the specs that pin component text are added or updated as the components change, including a new spec for D5's repository-wide check. Second, the distill size ceiling is recorded again once, with the value it replaces, and its measurement also counts the shared skills every distill run now loads. Third, the verdict's machine record accepts unconfirmed for criteria and guarantees, and older verdicts that say "unverifiable" stay readable. **Why:** The project's test-first rule needs a failing test before each component change, and the specs that pin component text live only in the executable's package. Distill measures 53,015 bytes against a ceiling of 53,024, so any addition to distill fails the existing size check. D6 needs the machine record, because a guarantee's result can only be held or broken today. The lead confirmed all three exceptions at this run's clarification gate. **Refuted alternative:** Keep the package entirely out of scope. An unconfirmed criterion would be stored as "unverifiable", a later run would copy an unconfirmed guarantee forward from the previous review's prose, and distill would be trimmed to fit the ceiling. This keeps the epic's line as written. It lost because no story would have a test, and copying from prose creates a second record of a result, which can go stale.
