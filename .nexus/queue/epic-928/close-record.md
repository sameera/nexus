# Close Record: Implement an epic unattended with one nexus command

## Key Decisions

- **D1 — The command is a verb of the shipped nexus executable (#966).** The command is a verb of the shipped `nexus` executable, written in the language of the rest of the command-line tool and listed among its commands. The two implement-epic scripts and their tests are removed in the same change. The command ships to adopters as an optional tool that the lead chooses to run. Analyze, close and distill stay stages, and none of them writes code. The same change adds the exception for this command to the product context's anti-goal and to the project instructions. **Why:** An adopter gets only the published package, so a script kept in this repository cannot reach them. A listed verb gets the usage listing and the dispatch checks every other verb has. It can also call the epic resolver, the verdict reader and the answer reader directly, without a second copy of any reader. **Refuted alternative:** Ship the existing shell script inside the package and expose it through a thin verb. That is the smallest change, and the script has been tested in use. It loses because the script reads the verdict by matching text and applies its own trust filter. That is a second copy of the trusted reader close uses, and it can drift from it. The script also needs bash and POSIX tools that the rest of the command-line tool does not need.
- **D2 — The command checks the epic and creates the branch before any agent stage (#966).** Before any agent stage, the command resolves the epic through the one epic resolver and refuses when a condition fails. The decision record must be approved. An epic that needs design must have a record. The working tree must be clean. The run's branch, named for the epic, must not exist yet. The command creates the branch itself, not the agent stage. **Why:** The old script found an unapproved record only when analyze refused, after a full implementation run. A refusal before any agent stage costs nothing. When the command creates the branch, the branch it may push is fixed before any model runs, so "never push the base branch" is checked by the command and not left to a prompt. A branch named for the epic also feeds the branch-name step of story resolution. **Refuted alternative:** Let the implementation stage create the branch, as the old goal did, and refuse afterwards to push from the base branch. It needs no naming rule. It loses because the command must then trust whatever branch the agent stage chose, and a run whose agent committed on the base branch finds out only after the work is done.
- **D3 — The implementation stage can end blocked, and the command checks the story commits (#966).** The implementation stage gets a goal that is met in one of two ways: the stories are done, or the blocked outcome. The goal tells the stage to do the record's "Before implementation" items first, to end with the blocked outcome when one of them cannot be done from the checkout, and to build each decision in the commit of the story that delivers it. After the stage, the command acts on the blocked line when there is one, and otherwise runs the story commit check. On either failure it stops before pushing. **Why:** A goal that can be met only by finishing keeps re-prompting a correctly stopped run until the turn cap, because nobody can clear the goal in headless mode. The second way to meet the goal ends the stage at once. The story commit check makes #929's first criterion something the command enforces. The old script only warned when a commit claim was missing. **Refuted alternative:** none
- **D4 — The draft pull request claims every live story under the scope-claim grammar (#966).** The command pushes and opens a draft pull request against the base branch, or reuses the branch's open pull request. The body claims every live story with a closing keyword under the scope-claim grammar. When the pull request does not live in the issues repository, each claim names the issues repository. **Why:** Close and analyze find a pull request's stories from its claims, and only claims that follow the grammar count. A bare number in a member repository's pull request names that repository's own issue. The old script copied commit trailers without a repository name, which finds nothing in a multi-repository workspace. **Refuted alternative:** none
- **D5 — Every analyze run in the loop publishes a verdict on the pull request (#966).** Every analyze run in the loop runs against the pull request and publishes a verdict. The command reads each round's results from the newest trusted verdict through the existing trusted reader. Local analyze rounds are dropped, and so is the separate certifying run at the end. **Why:** #930 requires the findings and their severities to come from the verdict. Only the published verdict carries per-finding data a script can read. A local run prints counts and nothing else. Publishing every round also removes the old failure where the local run and the pull-request run disagreed at the end, because there is only one kind of result. **Refuted alternative:** Keep local rounds, and change local analyze to print its findings in a form a script can read. That keeps the pull request quiet until the end and needs no worktree per round. It loses for two reasons. It changes analyze's local contract, which is outside this epic's scope. It also creates a second finding format beside the verdict, and the two can drift apart.
- **D6 — A fix round works only Critical, High and Medium findings (#966).** The work list holds the open Critical, High and Medium items of the newest verdict, departures and findings both. Low items are left off. A fix round is given each listed item's ID, severity, summary, fix text, location and files. It reads only the criterion, guarantee or decision each item cites, and never the epic or the record end to end. **Why:** The epic counts Medium findings as work and Low findings as noise. A short, precise list keeps a late round as small as the first. Departures are on the list because they are the record items analyze judged, and fixing code back to the record is in scope. **Refuted alternative:** Keep the old script's rule, which fixes Critical and High findings and then any Medium or Low finding whose fix stays in a file already touched. It saves rounds on cheap fixes. It loses because it changes code for Low findings, which the epic's success metric forbids.
- **D7 — A fix round sorts every finding before it edits anything (#966).** Escalations are found in two steps. First, a departure that the verdict marks as superseding a record decision is an escalation, with no agent stage spent on it. Second, the fix round sorts every remaining item before it edits anything. An item is an escalation when its fix would contradict a decision or guarantee the record states, or would meet a guarantee only by changing its wording. It is also an escalation when the fix is architectural: it adds a dependency, changes an interface or data format that another component or stage reads, or moves a responsibility between components the record names. When any item is an escalation, the round makes no change, the loop stops, and the command reports each escalation with its reason. **Why:** When the sorting happens before any edit, "no commit for it" holds for the whole round. The published verdict also stays current with the pushed head, so the lead can revise the record and continue from a true state. The first step catches the case the verdict already labels without spending an agent stage on it. **Refuted alternative:** Fix the fixable items in that round and stop after it. That makes more progress per run. It loses because the pushed head then has no verdict, and the lead must run analyze again before anything can be judged. The partial fixes may also be wrong once the record changes.
- **D8 — The loop compares open item IDs to detect a round with no progress (#966).** The loop ends clean when no Critical, High or Medium item is open on the newest verdict. It stops in three other cases: the set of open Critical, High and Medium item IDs is the same after a round as before it; the round cap is reached, which is 5 by default and which the lead can change; or an analyze run publishes no verdict. A stop lists the items still open. **Why:** A verdict keeps the same item ID for the same judged thing across runs, so comparing the sets of IDs tracks real progress. The old test compared a count and the head commit, and it missed a round that fixed one item and created another. **Refuted alternative:** none
- **D9 — Only the command posts answers, and only from what a person wrote before the run (#966).** Only the command posts answer lines, never an agent stage. The command posts an inferred answer only when the answer follows from something a person wrote before the run started: the approved record's text, the epic or story text, a decision stub committed before the run's first commit, or an earlier trusted answer on the same item. The command accepts departures and waives Critical or High findings. It never approves a deferral. Each answer it posts names its source and says that the unattended command posted it. An answer line that appears or changes during an agent stage stops the run and names the comment. **Why:** The run posts with the lead's account, and the trusted-author rule counts every such answer as the lead's. An answer drawn from scratch the run wrote itself would let the run approve its own departure. Naming the source lets a person check or overturn each answer. Keeping the posting in the command keeps the old guard that forbids models from answering. **Refuted alternative:** Keep record #871 D13 as it is, so that an unattended run never answers. That is the safest rule. It loses because #929 asks for answers that can be inferred.
- **D10 — The pull request is marked ready only on a current, clear verdict (#966).** Before it marks the pull request ready, the command checks the newest trusted verdict. The verdict must be for the pull request's current head, and no Critical, High or Medium item may be open. The command then rewrites the run status section and marks the pull request ready. **Why:** Close and the merge pre-check read the published verdict. "Ready" must mean that the verdict they will read is current and clear. **Refuted alternative:** none
- **D11 — Every stop rewrites one status section of the pull request body (#966).** Every stop goes through one path. That path exits non-zero, prints the stage and the reason, and rewrites the run status section of the pull request body when a pull request exists. It never posts a comment for a stop. When rewriting the body fails, the command reports that and keeps the non-zero exit. **Why:** Five earlier runs failed without anyone noticing, because a draft whose body still said "analyze runs next" looked like a run that never got there. The body is what a reader sees first. Rewriting one section gives the same result on every run. **Refuted alternative:** Post one comment per stop. That keeps a history of stops. It loses because the body still shows a stale status, and every new run adds another comment.
- **D12 — Each prompt is written once, and the command judges only harness-neutral output (#966).** Each agent stage's prompt is written once. One launcher with a Claude form and a Codex form starts the stage and turns command names into that harness's form. Every decision the command makes reads git, the issue graph, the verdict, or the fixed-prefix lines of the final message. It reads no other harness-specific output. **Why:** Model output cannot be identical across harnesses. The command's checks and stop rules applied to that output can be identical. **Refuted alternative:** none
- **D13 — The command does not use /nxs.code-review (#966).** The command does not use `/nxs.code-review`. Any code-review loop belongs to the deferred epic. **Why:** The epic's description defers the code-review loop and the ranking post, and no criterion of either story reads a ranking. The epic wins over its own outdated assumption. It also wins over initiative #937's execution order, which makes this epic wait on #918. That wait cost nothing, because #918 is closed, but this design uses nothing #918 delivered. **Refuted alternative:** none
- **D14 — The test command and the base branch resolve from the invocation, then from settings (#966).** The test command comes from the invocation argument, then from one new key read through the shared settings resolver. When neither gives a value, the implementation stage finds the suite itself and names the command it ran in its final message, and the run status section records that command. The base branch is the invocation argument when one is given, and otherwise the repository's default branch. **Why:** The old default was this repository's own test command, which is wrong in any adopter's repository. The shared resolver is the one place settings are read. The existing worktree-base key holds a directory, not a branch, so it cannot serve as the base branch. **Refuted alternative:** Refuse to start when no test command is declared. That is the strictest rule. It loses because it makes every adopter set a key before a first run, when most repositories state their suite plainly.
- **D15 — Claude stages run in auto permission mode by default (#966).** Claude stages run in auto permission mode by default. When auto mode is unavailable to the lead's account, the command refuses before any agent stage and names the option that sets another mode. The lead can pass another mode, such as bypass, explicitly. Codex stages run in a workspace-write sandbox. The command prints the mode at start. **Why:** A headless stage cannot answer a permission prompt, so a mode that prompts produces a run that does nothing. Auto mode approves safe actions and blocks risky ones without prompting, and a blocked action returns to the stage as a refusal instead of a wait. That keeps the run headless without giving it everything the lead's account can do. Refusing when auto mode is unavailable keeps a silent widening to bypass from happening on an adopter's machine. **Refuted alternative:** Default to bypass for Claude stages, as the old script did. It never blocks a stage on any repository. It loses because an adopter's run could then do anything the lead's account can do on that machine, without the lead having chosen that.
