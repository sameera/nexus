# Close Record: A Coherent Decomposition Files an Initiative

## Key Decisions

- **D1 — The objective is proposed inside the existing consent choice (#786).** The objective is proposed inside the existing consent choice, not as a second question. On the XL gate, the stubs option becomes two options: stubs under the initiative, and stubs filed flat. On the L gate, the split option is divided the same way. Neither version is marked as recommended. An answer that rewords the objective counts as accepting it in the lead's words. **Why:** The lead must accept or decline before anything is created, and one choice keeps the gate to one interactive point. Marking the initiative as recommended would turn the lead's judgement into approval of the model's reading. This gate is the only place where that reading can be rejected. **Refuted alternative:** Keep today's options and add a separate objective question in the same prompt. This leaves the existing options untouched. It lost because the objective question means nothing when the lead chooses to file one full epic. Two independent answers can also combine into a state the gate then has to explain.
- **D2 — An objective is always proposed on the decomposition path (#786).** When a decomposition has two or more goals, an objective is always proposed. The model cannot withhold it. The lead's decline is the only filter. **Why:** A decomposition splits one capability the lead described, so an objective drawn from that description is not invented. Letting the model withhold it would add a third branch to the gate and a second judge. It would also contradict the first criterion of #706. **Refuted alternative:** Let the model withhold the proposal and state its reason when it judges that the stubs share no objective. This protects a hurried lead from accepting a weak objective. It lost because on this path the objective is bounded by the lead's own description. The epic makes the lead's decline the judgement, and a model veto adds a branch that has to be tested and explained.
- **D3 — Only a decomposition in `/nxs.epic` proposes an objective (#786).** Only a decomposition in `/nxs.epic` proposes an objective. These never propose one: the approval gate's deferral stub, the stubs `/nxs.close` files for deferred scope (even when there are several), the intake lane's follow-ups, a decomposition with one goal, and the successors of a stub that already sits under an initiative. **Why:** Deferred stubs have no shared objective by construction, and one stub has no set to group. As written, the phrase "a run is about to file more than one stub" would also catch a close that defers several stubs. Successors are covered by D10. **Refuted alternative:** none
- **D4 — The gate shows everything the initiative will state (#786).** The gate shows the objective, the execution order and every reach statement. The lead accepts or declines them as one unit. In discovery mode the objective is the discovery's destination, in its own words. From typed intent the objective is drafted from the lead's capability description and may claim nothing beyond it. **Why:** Editing the initiative after filing is out of scope. So any text first seen on the filed issue would be permanent text that nobody approved. The epic assumes that a discovery already states its outcome, so drafting that outcome again would be invention. **Refuted alternative:** none
- **D5 — The initiative is its own declared kind (#786).** The initiative becomes a declared kind with its own marker, resolved only through the shared publishing settings. The label defaults to `initiative`. The issue type has no default, like the epic type. The kind rule recognises an initiative as its own kind; today such an issue falls into "none of these". In a repository that marks issues by issue type and declares no initiative type, the gate names the missing setting and offers only the flat filing. **Why:** The parent check (D8) and the resolver refusal (D11) both need a positive marker to test. The classification rules forbid working out a kind from the issue graph, and they forbid guessing an issue-type name. Resolving the marker before consent means the lead is never offered an option that fails after they agreed to it. **Refuted alternative:** none
- **D6 — The initiative is filed first, then the stubs, then the numbers (#786).** The initiative is filed first, as its own one-item batch with no parent. The stubs are filed next, with the initiative as their parent. The run then applies the finishing rewrite once. Each step can be repeated safely, and the run folder is kept until all three are complete. **Why:** A stub's parent must be an existing issue number, so the initiative has to exist first. The filer's reference rewrite resolves names only within one batch, so the stub numbers can only be written in after the stubs are filed. Keeping every parent link inside the guarded filer means no second write path needs its own copy of the parent check. **Refuted alternative:** File the stubs flat first, then file the initiative with real numbers in its body, then attach the stubs to it. An interrupted run would then leave exactly the flat filing, which is a milder failure. It lost because attaching after creation is a new parent-link path outside the filer, so the rule that a stub is never under an epic would have to be enforced in a second place.
- **D7 — The order follows the stubs' blocking edges (#786).** The execution order respects every blocking edge between the stubs. Ties are broken by the decomposition's own order. Each entry carries a cumulative reach statement in plain words, and the last entry says the objective is reached. There are no percentages. The body holds no table and no second list of children. **Why:** The epic requires the body's order and the stubs' own edges to describe the same sequence. Deriving one from the other is the only way both agree on the day of filing. A percentage would claim a precision nobody has. GitHub already shows the children, so a table would repeat it. **Refuted alternative:** none
- **D8 — The filer allows only an initiative as a stub's parent (#786).** The filer's refusal narrows from "an unplanned item never names a parent" to "an unplanned item may name a parent only when the kind rule reads that parent as an initiative". Any other parent refuses the whole batch before anything is created. That includes an epic, a story, a record, an unmarked issue, and a number that does not resolve. The check reads from GitHub only for unplanned items that name a parent. It uses the same kind rule the resolver uses, not a copy. The instructions in `/nxs.epic` and `/nxs.close` that say a stub is never a sub-issue of anything are reworded to match. **Why:** The refusal exists to prevent one deadlock: a stub inside an epic's own children blocks that epic's close. An initiative sits above the epic, and closing an epic never reads its parent. Allowing only initiatives, and refusing everything else by default, keeps the old guarantee. **Refuted alternative:** Let the writing stage declare the parent's kind with a flag, and trust the flag. This needs no read from GitHub and keeps the check local. It lost because the refusal exists so that writers are not trusted to get parentage right, and a flag brings that trust back.
- **D9 — The run confirms every stub is attached (#786).** After the stubs are filed, the run reads back the initiative's children. If any stub is missing, the run reports itself incomplete and keeps the run folder. When the filer re-runs, it retries the parent link for any issue it already filed. Retrying is safe because a link that already exists counts as success. **Why:** Today a failed parent link only prints a warning, and the batch still reports complete. Left as is, a stub could silently drop out of the initiative, which breaks the first criterion of #708 with no way to recover. **Refuted alternative:** Keep the filer's warn-only behaviour and tell the lead to attach any missing stub by hand. This changes no shared filer behaviour. It lost because a link attached by hand bypasses the parent check, and the run cannot confirm the recovery step.
- **D10 — Successors of a split stub join the same initiative (#786).** When a promoted stub that sits under an initiative proves larger than one epic, its successors are filed as children of the same initiative. No new objective is proposed. The original stub is closed as not planned and names its successors, as today. The initiative's body is not edited. **Why:** The successors serve the objective the original served. Filing them flat would remove them from the grouping, so a lead browsing the initiative would not find them. A second initiative would split one objective across two parents. **Refuted alternative:** File the successors flat and leave the initiative alone. This keeps the rule of one decomposition run per initiative literally true, and the body and the children stay consistent. It lost because the successors disappear from the only place a lead looks for the set.
- **D11 — Every stage refuses an initiative as its epic (#786).** The epic resolver refuses any issue whose kind is initiative, and names it as an initiative. This applies to every stage, not only to an import. The check reads only the initiative marker. It adds no failure for an issue that is not an initiative, and none when no initiative marker is declared. **Why:** The epic assumes an initiative is never the target of a decision record or a conformance check, and today nothing enforces that. An initiative with no parent resolves as an epic, with its stubs read as stories. The close and analyze stages can also reach an initiative by walking up from a branch whose linked issue is an epic. More initiatives make that path more likely. **Refuted alternative:** none
- **/nxs.epic reads the initiative's body back, replaces each STUB-<NN> from the stubs' ledger, and writes it with gh issue edit.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** The record's mechanism names it the run's single edit, and the filer's own rewrite pass stays scoped to one batch. **Refuted alternative:** A nexus capability that performs the rewrite deterministically; it adds a registered verb for one substitution.
- **The initiative batch and the stubs batch both run with --keep-manifest; the ledgers in the run folder are the record of what was filed.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** A repeat then reuses the filed issues through the filer's existing resume path, with no second bookkeeping file to drift from it. **Refuted alternative:** A separate initiative.json the command writes by hand after filing.
- **The kind rule tests the initiative marker last, after epic, story and record.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** A repository whose epic-label is `initiative` would otherwise have every epic refused as an initiative. **Refuted alternative:** Test the initiative marker first, so an issue carrying both markers is refused as an initiative.
- **Under `types`, a label-only initiative reads as `other`, as it did before the kind existed.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** The record says the initiative kind adds no failure for an issue that is not an initiative under the declared marker. **Refuted alternative:** Extend classification-mode-mismatch to initiatives, which would fail hand-labelled initiatives in a types-mode repository.
- **The shared kind module gains readKindMarkers and isDeclaredInitiative; the resolver's refusal and the filer's parent check both call them instead of classifyIssueKind.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** classifyIssueKind can fail with a mode mismatch or an unresolved classification, and the record says the refusal adds no failure for an issue that is not an initiative. **Refuted alternative:** Call resolveKindClassification and classifyIssueKind on every resolve, which would fail a types-mode repository that declares no epic type on stages that resolve it today.
- **nexus create-story --dry-run makes the read-only parent read when a stub names a parent.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** The old refusal applied to a dry run too, and a rehearsal that previews a batch the real run refuses is misleading. **Refuted alternative:** Skip the check on a dry run, so a rehearsal still reaches nothing at all.
- **The filer keeps warning on a failed link and retries it on a repeat; /nxs.epic reads the initiative's children back and is what reports the run incomplete.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** The record's D9 places the confirmation in the run, and the filer's end-of-run report is a frozen surface. **Refuted alternative:** Add a parent-link line to the filer's report and exit non-zero on a failed link, which changes every story batch.
- **resolveRecordClassification and its types moved to the settings layer beside the kind rule; classifySubIssue, withdrawal and the unplanned-label helpers stayed in the resolver.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** The kind rule calls the record resolution, so leaving it behind would keep the circular dependency the move exists to remove. **Refuted alternative:** Move only classifyIssueKind and pass the record markers in from each caller.
- **The successor paragraph in /nxs.epic adds --keep-manifest to step 4 and holds step 6 until every successor is one of the initiative's children; step 6's skip condition names the case.** (a decision stub the verdict on sameera/nexus#914 confirmed). **Why:** Without the ledger, the instructed repeat of step 4 files every successor a second time. **Refuted alternative:** Fold the fix into the unreleased 0.101.0 entry instead of a new patch release.
